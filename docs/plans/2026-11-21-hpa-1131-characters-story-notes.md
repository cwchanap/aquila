## Goal, in and out

Readers can open a **Characters** page while reading or via **My Progress**, see only character identities and facts supported by completed story progress, and return to the same place in the reader. Notes are static, compiled story content, not a new service or a writeable achievements store.

**In:** simple per-story notes Markdown; Chinese dialogue unlock fences and implicit character-meeting events; compiler-generated small note data; a pure spoiler-safe selector built on the existing story-map ancestor walk; shared responsive Characters UI hosted on a page and in ReaderShell; Notes button, My Progress chip for stories that actually have notes; localizations and The Platform at the End of the World Acts 1–3 pilot; targeted unit/component/browser E2E and visual acceptance.

**Out:** Mysteries tab, toast/dot/New markers, notes for later Acts 4+ or other stories, new storage or progress API, database, sync migration, new voice/audio/art assets, generalized note CMS, and unrelated reader refactors. HPA-1132 extends this foundation later; do not scaffold an unused mystery feature now.

## Authoring and generated data contract (KISS)

1. Use a tiny Markdown parser with **no YAML, CMS, new dependency or generic framework**. In zh notes, each section starts with “## &lt;character_id&gt;” followed by optional “hidden: true” (default false), **optional “known-as: &lt;label&gt;” for a .met-before-speech character**, and zero or more “- &lt;fact_id&gt;: &lt;text&gt;” fact lines. All IDs and structural flags are defined by zh. **Do not author canonical zh name**; take it from ParsedCharacterDirectory. Do not author known-as for characters met by speech alone.
2. Validate each character ID with charDir.getById from docs/characters.md; skip the narrator card. Fact IDs are lowercase snake_case, unique within a character, and reject identifiers in the existing RESERVED_OBJECT_PROPERTY_NAMES set when keyed as plain records. Missing localized fields fall back by ID to zh.
3. en/ja notes may override fact text and optionally “name: &lt;canonical localized name&gt;”. They may supply matching “known-as:” only if the zh section declared it for the .met case. They cannot add new characters, facts or structural fields. Source canonical names and locale conventions from docs/characters.md and docs/translation-glossary.md.
4. In **Chinese dialogue scripts only**, a standalone fenced “unlock” block names one stable target such as “li_jie.age”, “li_jie.name”, or “li_jie.met”. It applies to the immediately following dialogue entry. Multiple pending unlock blocks before an entry and repeated target markers on alternative routes are legal; a dangling/malformed block fails compilation. These blocks are not dialogue entries and leave index, character, bg, sfx/bgm, flow and locale alignment unchanged. Existing localize.ts already rejects en/ja dialogue fences.
5. **Meeting and names are separate.** A character becomes met when its first **reached spoken dialogue line**, a reached .met marker, or any reached .name/fact marker occurs. A character's canonical **name becomes known** when either a reached .name marker fires **or a reached Chinese speaker displayName after standard suffix stripping equals the registry's canonical zh name**. Thus Li Jie is known naturally when he first says “李杰” in Act 1; the other students keep their in-story descriptive labels through Acts 1–3 without artificial .name fences. A .name marker is optional. Build validation checks unknown .name targets, but **does not require each name to be revealable** (the majority of pilot identities are deliberately not named yet).
6. **Known-as labels:** when met by speech, derive the descriptive label from the first **eligible reached** spoken event for that character. Record the zh speaker header plus corresponding en/ja header at the same entry index; use the source fallback when a mirror scene is untranslated and strip suffixes with the existing resolve-character logic. For someone first met through a .met marker **before speaking**, use the optional authored known-as label in zh/en/ja (e.g. Emi “文靜少女” / “Quiet Girl” / “物静かな少女”, Ling Mo “神秘黑衣男” / “Mysterious Man in Black” / “黒衣の謎の男”). If no label exists, use a generic anonymous label. A known-as field **requires at least one .met marker**, otherwise fail the build to prevent duplicated labels for ordinary speaking characters. Once a canonical name is known, switch to it.
7. **Determinism when branches were explored:** “first reached” cannot be recovered chronologically from the unordered visited union, so do not promise literal first-ever encounter. Choose a stable representative spoken label by **smallest breadth-first depth from flow.start**, then prefer a scene on the *current route's ancestor chain* for ties, then lower entryIndex, then lexicographical sceneId. Derive BFS depth alongside the existing indexed flow; reuse its traversal/parent data and keep this rule testable. Never use visited-array order or a second persisted history.
8. **Keep runtime notes small:** emit at most **one implicit spoken-meet event per (characterId, sceneId)** at the first spoken entry within that scene; later speech in the same scene adds no useful meeting event. Keep the original sourcePath/entryIndex in compiler diagnostics, **omit sourcePath from generated runtime notes.ts**. Emit only sceneId, entryIndex, stable note target and compact localized labels/definitions. The registered notes importer dynamically imports generated/&lt;story&gt;/notes and generated/&lt;story&gt;/flow directly, **never** stories/&lt;story&gt; (which statically imports full dialogue by locale).
9. **Build validation:** fail with actionable source locations on unknown/duplicate/reserved character/fact IDs, unknown fact targets, invalid/dangling fences, notes facts never unlocked on any route, orphan en/ja IDs, and a character that can never be met by *any* speech, .met, .name or fact marker. No build failure for intentionally unrevealed canonical names. A valid repeated unlock on different branches is not a duplicate fact definition. Do not add a second scene alignment checker.
10. For this ticket only train_adventure has notes. Advertise availability through a Partial&lt;Record&lt;RegisteredStoryId, NotesImporter&gt;&gt; map, export hasStoryNotes/loadStoryNotes via async/index.ts, and cache in-flight/loaded imports keyed by story ID similarly to the existing story content loader. A missing importer gives a localized unsupported/empty page, no reader trigger, and no My Progress chip. Avoid any eager import of the story dialogue bundles.

## Spoiler safety: one shared proof-of-passage rule

**Critical review fix:** Visited means **entered**, not finished. A reader may enter Act 3, stop at line 5, and jump to Act 1; sync can also union an unfinished Act 3 from one device with Act 1 as the current saved position. **No non-active visited scene may unlock its later lines merely because it appears in visited.**

Add **passedSceneIds(flow, progress, currentSceneId)** beside visibleSceneIds in apps/web/src/lib/story-map.ts. Reuse the existing indexed flow/ancestor traversal; do not build a separate graph walker. It identifies:

- **Passed in full:** strict ancestor **scenes** of each reached scene in the union of progress.visited and the current scene. Also include completed progress.endings **and their strict ancestors**. The ending scene itself counts as completed only when recorded in endings.
- **Current in-progress:** events in the active scene with event.entryIndex ≤ its current displayed dialogueIndex; **unless** that scene is already in the fully passed set, in which case all of its events remain unlocked (e.g. jumping back from Act 3 to replay Act 1 at line 1).
- **All other scenes:** locked. In particular, a visited but unfinished **non-active** scene is not passed. Never use visited-array insertion order or freshness timestamps as proof of completion; cloud unioning makes that unreliable.

This selector lives in **apps/web/src/lib/character-notes.ts** and receives notes, the lightweight flow, StoryProgress and optional ReaderShell live position. A standalone page and My Progress use the current saved position and progress. It returns one spoiler-filtered model for counts, met/secret/hidden/known-as/name/fact states and act provenance. An item can unlock through the same target on any completed route; a later unreached marker cannot unlock it.

**No progress migration.** The visited ledger may be absent or trimmed; ancestors of a known current scene and recorded endings still count, while unsupported facts stay locked. Known conservative limitation: facts from an unfinished scene you left and did not complete may disappear until you return or pass that scene. That is preferable to a spoiler leak and can be handled without new storage.

The graph is currently tree-shaped; existing story-map code already warns on merged paths and keeps the first parent link. Reuse that assumption here; merged-graph support is out of scope.

## UI and behavior (per Linear mock-up)

**Desktop:** scrollable cast rail with round portrait/avatar, label and unlocked-fact count; selected detail with shown facts and act provenance, roughly 40% portrait region where a provider is available, and generic blank bars for locked facts. Unmet non-hidden characters render anonymous “?” rows, while hidden twists are absent from rows/counts until met. Only Characters is shown; no placeholder Mysteries tab.

**Phone:** three-column card grid; tap to open full-screen detail with portrait/initials at top and Back/Close. Provide safe-area padding, 44px touch targets, no overflow, and no unrevealed information in text, image alt, tooltip or aria. **Met but unnamed** characters may show their known-as label and base portrait; **unmet**/hidden characters must not show a portrait. The base portrait represents someone already seen, not proof their real name was learned.

**Shared presentation:** one Characters component with optional **portraitUrl(characterId): string | null** callback. In Visual Novel mode, the reader can use its *already initialized* visual runtime. Add a narrow synchronous method to VisualReaderRuntime in apps/web/src/lib/visual-assets/source-factory.ts:

`resolvePortraitUrl(characterId: string): string | null` reads from the active WebAssetResolver with `resolver?.resolve({ type: 'portrait', key })`, where `key` is `<character_id>/base`; return `result.webpUrl.href` only when status is `resolved`, else null. The resolver is already a closure variable; do not expose it or create a new source. **train_adventure** has `suppressPortraits: true` for its stage overlay, but that must **not** prevent the separate notes view from resolving a validated base portrait. Derive the injected callback reactively in ReaderShell from both visualRuntime and visualIdentity so the cards update when the release becomes available. Text mode (visualRuntime null), the standalone Notes page and My Progress all use **initials** without starting a visual runtime, importing scene dialogue or fetching the asset-release pointer. The fallback initials derive from the *visible safe label*, not an unrevealed canonical name.

**Reader overlay and entry points:** ReaderShell owns exactly **one** Notes sheet and notesOpen state. Settings is **not** mounted on a normal phone text reader: `settingsAvailable = readerMode === 'visual' || !isMobile || isBlocking`. When Settings **is** mounted (desktop text and desktop/phone Visual Novel), put one sibling 44px `#reader-notes-trigger` immediately left of it. In regular **mobile text mode** (`isMobile && readerMode === 'text' && !isBlocking`), instead pass `notesAvailable` and `onOpenNotes` to MobileNovelReader and render an icon button in its existing auto-hiding chrome bar near Story Map (same 44px target and longpress tooltip). **Do not** position a floating Notes button over that chrome/progress bar or keep it visible while chrome is hidden. The one shared sheet is accessible from both paths.

**Overlay behavior:** add notesOpen to the existing leafDisabled/triggerUnavailable and mutually exclusive Settings/StoryMap/Crossroads/ending guards. Make `openNotes()` refresh `getCurrentStoryProgressSnapshot()` exactly when opening, similar to openStoryMap, so newly recorded progress is reflected. For focus restoration, use `#reader-notes-trigger` when settingsAvailable, and `#mobile-reader-menu-trigger` after opening from phone text-mode chrome (which hides on opening); extend `overlayFocusTarget` accordingly. Reuse focusTrap, Escape, scrim, Close and input-inert behavior. Closing Notes changes **none** of reader story/scene/index, URL, storage record or ongoing BGM/voice; it must not mount a new reader or pause, stop or dispose audio. Notes is hidden for stories without an importer.

**Standalone page:** /[locale]/notes?story=train_adventure; no tab parameter. Validate the story ID using isRegisteredStoryId. Unknown/not-supported stories get a localized empty/selection state without silently loading another story. Use owner-aware StoryProgressView and the shared Characters component with an initials provider. The existing zh/ja proxy generator picks up new [locale]/notes.astro; do not edit generated proxy pages.

**My Progress:** make the existing full-row anchor and Characters link **sibling interactive destinations** in one wrapper, preserving Continue/Read again styling and keyboard behavior; no nested anchors. For started stories where hasStoryNotes(id) is true, start an **asynchronous** load of just that story's small compiled notes and flow, with a cached in-flight promise. Count from the same spoiler-safe selector after load. **While loading or on failure**, keep a usable Characters chip without a numeric count; never block the progress row or crash the page. No loading for the other seven stories; no dialogue or visual imports. Keep count fresh when account-scoped progress changes.

**Localization:** en/zh/ja UI labels, note facts and optional names with per-field zh fallback; known-as labels from the matching compiled scene mirror or fallback authorship for .met. The selected fact's provenance uses existing extractActName/actLabel; don't create a second formatter. No canonical identity or unreached note leaks via accessible names, alt text or URLs.

## Review disposition and trade-offs

- **Round 1:** [review #6009534645](https://github.com/cwchanap/aquila/pull/149#pullrequestreview-6009534645) — retained strict passed proof, simplified character note authoring, lazy notes importer and unit/component-first checks.
- **Round 2:** [review #6009767233](https://github.com/cwchanap/aquila/pull/149#pullrequestreview-6009767233) — accepted all five additional findings: optional .met-only known-as, implicit canonical speech name reveal and met-portrait visibility; phone text-mode chrome trigger and focus; one-per-scene spoken events with deterministic label selection; narrow VisualReaderRuntime portrait resolver; direct dialogue-free dynamic imports and async My Progress count.
- **Safe-but-conservative limitation:** facts from an unfinished scene that the reader exits may disappear until re-entering it or reaching a descendant; the existing progress schema does not store per-scene partial high-water. Do not add a migration or event store to solve this hobby-project edge case.
- **Historical label limitation:** an unordered union of visited scenes does not encode exact first-encounter chronology; BFS depth + active route gives deterministic, defensible labels without another state model.
- **Tree-shaped flow assumption:** story-map already treats merged graph paths as unsupported. Reuse its walk instead of building a new engine.
- **Scope:** one PR, no speculative abstraction, no network service, no new art/audio generation, no native acceptance for a web-only change.
